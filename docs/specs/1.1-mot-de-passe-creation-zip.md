# Spécification — 1.1 Mot de passe à la création ZIP

## Contexte

LibreRAR sait lire des archives chiffrées (ZIP AES, RAR, 7z AES-256) mais la
création d'archive ZIP produite par `create_zip` est en clair. C'est l'écart
le plus visible face à WinRAR/7-Zip : un utilisateur qui migre perd la
possibilité de protéger ses archives.

## Objectif

Permettre à l'utilisateur de protéger l'archive ZIP créée par un mot de
passe, chiffré **exclusivement en AES-256** (ZipCrypto, cassable en quelques
minutes, est proscrit).

## Critères d'acceptation

1. L'UI offre un champ optionnel de mot de passe (avec confirmation) dans le
   panneau de création ; sans mot de passe, le comportement actuel est inchangé.
2. Un mot de passe vide ou blanc est traité comme « pas de mot de passe ».
3. Les deux saisies doivent être identiques, sinon la création est bloquée
   avec un message d'erreur explicite en français.
4. Backend : `create_zip` accepte `password: Option<String>` ; les entrées
   sont chiffrées AES-256 (`zip::AesMode::Aes256`, feature `aes-crypto`
   déjà activée).
5. Contrainte bibliothèque : `ZipFileBuilder` (pool parallèle) refuse les
   options chiffrées — une création chiffrée passe intégralement en flux
   séquentiel (`start_file`), ce qui borne également la mémoire.
6. Round-trip testé (cargo) : sans mot de passe → échec typé
   `PasswordRequired` ; mauvais mot de passe → échec ; bon mot de passe →
   contenu identique. Le listing (en-têtes) reste possible sans mot de passe.
7. Aucune archive partielle en cas d'échec (comportement existant conservé).
8. `npm run lint`, `npm test`, `npm run build` et `cargo test` passent.

## Hors périmètre

- Auto-extractibles (SFX), volumes découpés : refusés par la roadmap.
- Chiffrement 7z à la création (tâche 1.2).
- Consentement de la Modification de `tauri.conf.json` : non requis.
